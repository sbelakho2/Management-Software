4. Database lifecycle (thirtieth-audit item 26):
   The chart ships three DB Job hooks that run before every install/upgrade
   rollout, in this order:
     bootstrap (ADMIN) -> migrate (sensei_migrator) -> grants (ADMIN) -> rollout
   - The API/workers NEVER auto-migrate (DB_AUTO_MIGRATE=false) and connect
     ONLY as sensei_app (DATABASE_URL_APP); admin/migrator URLs live in the
     Secret but are never mounted into API/worker pods.
   - A failed hook Job aborts the release: on upgrade the previous
     deployment keeps serving traffic (hooks complete before the new
     manifests are applied).
   - Watch them with:  kubectl get jobs -l app.kubernetes.io/instance={{ .Release.Name }}
     (failed pods are kept for logs; succeeded hook Jobs are deleted).

5. Seed the CEO account:
  The CEO seed account is created at first startup when SENSEI_CEO_PASSWORD is
  set (via the {{ include "sensei.fullname" . }}-secret Secret). Set it before
  the first deploy:
    helm upgrade --install ... --set config.ceoPassword="<strong-password>"

6. Health endpoints (probes):

** Important Security Notes **
- Three DB identities are defined (thirtieth-audit item 26):
    DATABASE_URL_ADMIN      -> db-bootstrap + db-grants Job hooks only
    DATABASE_URL_MIGRATOR   -> db-migrate Job hook only
    DATABASE_URL_APP        -> API + workers only
  API/worker pods never receive the admin or migrator URLs. All other
  credential-bearing variables (JWT_SECRET, S3_ACCESS_KEY, S3_SECRET_KEY,
  SMTP_PASSWORD, NATS credentials, SENSEI_CEO_PASSWORD) live in the
  {{ include "sensei.fullname" . }}-secret Secret; the ConfigMap holds
  non-secret configuration only. See .env.example for the canonical
  environment contract.
- SENSEI_ENV is parsed strictly: an invalid value (e.g. a typo) aborts startup.
- JWT secrets are preserved across upgrades; rotate them deliberately.
